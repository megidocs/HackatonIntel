# הערכת ידע ליבה · תקשורת בין מחשבים ובאינטרנט

קרא קודם את [הפרוטוקול המשותף](../assess-core-knowledge/protocol.md) ופעל לפיו. הקובץ הזה מגדיר רק את התוכן.

**סעיפי אפיון:** [6.5 תקשורת](../../../docs/specification.md#65-תקשורת-בין-מחשבים-ובאינטרנט-networking), 4 ארכיטקטורה.

## מושגי ליבה

1. מודל השכבות: אפליקציה (JSON), תעבורה (TCP), רשת (IP), קו (Wi-Fi או סלולרי). כל שכבה עוטפת את הקודמת.
2. כתובת IP, port ו-DNS. מה קורה מרגע הפנייה לשם השרת ועד שנפתח חיבור.
3. HTTP/REST לפעולות חד-פעמיות, WebSocket לעדכונים רציפים. WebSocket נפתח בבקשת HTTP Upgrade.
4. TCP מול UDP: אמינות וסדר מול מהירות. Head-of-line blocking.
5. schema להודעה, וחותמת זמן (ts).
6. אמינות: heartbeat, reconnect, טיפול בהודעות שהגיעו שלא לפי הסדר.
7. Push Notifications (‏FCM/APNs) כשהאפליקציה ברקע.
8. Latency ו-RTT. רוחב פס וגודל הודעה.
9. TLS: ‏HTTPS ו-WSS.

## בנק שאלות

### מושג

- **מה קורה להודעת מיקום בכל שכבה בדרך מהטלפון לשרת?**
  תשובה טובה: JSON באפליקציה; TCP מחלק לסגמנטים ממוספרים עם port; ‏IP מוסיף כתובות מקור ויעד ומנתב; שכבת הקו מעבירה מסגרות ב-Wi-Fi או ברשת הסלולרית. בצד השני, כל שכבה מסירה את העטיפה שלה.
- **מה תפקיד ה-DNS?**
  תשובה טובה: מתרגם שם לכתובת IP. קורה לפני פתיחת החיבור, ובדרך כלל נשמר במטמון.
- **מה ההבדל בין TCP ל-UDP?**
  תשובה טובה: ‏TCP מבטיח שהנתונים יגיעו ובסדר הנכון, עם חיבור ושליחה חוזרת. ‏UDP שולח בלי הבטחות, מהר יותר ובלי עיכוב של המתנה.

### החלטה במערכת

- **למה מיקום נשלח ב-WebSocket ולא בבקשת HTTP כל 200 מילישניות?**
  תשובה טובה: חיבור אחד פתוח לאורך זמן, בלי לחיצת יד וכותרות בכל הודעה, והשרת יכול לדחוף עדכונים ללקוח בלי שיבקש.
- **ולמה ההתחברות ופתיחת אירוע עוברות ב-REST?**
  תשובה טובה: פעולה חד-פעמית עם תשובה אחת. ‏REST פשוט, ומתאים לבקשה ותשובה.
- **למה אפליקציית האזרח צריכה גם Push Notifications?**
  תשובה טובה: מערכת ההפעלה סוגרת את חיבור ה-WebSocket כשהאפליקציה ברקע, כדי לחסוך סוללה.
- **למה בכל הודעה יש שדה ts?**
  תשובה טובה: כדי לסדר הודעות שהגיעו שלא לפי הסדר, למדוד זמן מקצה לקצה, ולזהות הודעות ישנות (קשור ל-Replay ב-6.1).

### חישוב

- **רוחב פס.** בחר מספר רכבים (למשל 40) וקצב עדכון (5 בשנייה), והצג הודעת JSON חדשה באורך של בערך 80 עד 120 בתים. שאל: כמה בתים בשנייה מגיעים לשרת? אם השרת שולח כל עדכון ל-M לקוחות, כמה יוצא ממנו? מה נחסוך עם הודעה מצומצמת של 30 בתים?
  תשובה טובה: רכבים × קצב × גודל. ביציאה, כפול מספר הלקוחות. החיסכון הוא ההפרש בגודל ההודעה כפול אותו קצב. בתשובה מצוינת התלמיד מציין שגם הכותרות של TCP ו-IP מוסיפות לכל הודעה.
- **Latency.** בחר RTT (למשל 60 מילישניות ב-Wi-Fi ו-150 בסלולרי). שאל: אם היעד הוא פחות מ-300 מילישניות מהטלפון למסך המוקד, האם הוא מושג? מה עוד נכנס לזמן הזה?
  תשובה טובה: חצי RTT בכל כיוון, ועוד זמן עיבוד בשרת וזמן רינדור. ‏RTT הוא הלוך-חזור, ולא כיוון אחד.

### מה אם

- מה קורה אם חבילה אחת של WebSocket הולכת לאיבוד?
  תשובה טובה: ‏TCP שולח אותה מחדש, וכל ההודעות שאחריה מחכות (head-of-line blocking). המיקום מתעכב גם אם הוא כבר ישן.
- מה אם רכב החירום נכנס למנהרה ויוצא אחרי 20 שניות?
  תשובה טובה: ה-heartbeat מזהה ניתוק, הלקוח מתחבר מחדש, והשרת מסמן את המיקום כלא עדכני בינתיים.
- למה לא להעביר את המיקום ב-UDP?
  תשובה טובה: אפשרי, ונוח למיקומים כי ממילא רק האחרון חשוב. אבל דפדפן לא תומך ב-UDP ישיר, ו-WebSocket נותן הצפנה ופשטות.

### איתור שגיאה

```javascript
socket.onmessage = (e) => {
  const loc = JSON.parse(e.data);
  units[loc.unitId] = loc;          // always overwrite with the latest arrival
};
```

תשובה טובה: הודעה ישנה שהגיעה מאוחר דורסת מיקום חדש. צריך להשוות `ts` ולהתעלם מהודעה ישנה יותר.

## טעויות נפוצות לזיהוי

- "WebSocket מחליף את TCP." הוא רץ מעליו.
- "UDP לא אמין, ולכן גרוע." חסר: מתי זה בסדר.
- בלבול בין latency לרוחב פס.
- "הטלפון ממשיך לקבל WebSocket ברקע."

## דירוג ספציפי לנושא (רכיב A, סולם מודל ה-T)

- **4 · מצוין:** עוקב אחרי הודעה בכל השכבות, מנמק WebSocket מול REST ואת ה-push, מחשב רוחב פס עם ערכים חדשים, ומזהה את בעיית הסדר.
- **3 · טוב:** כמו ברמה 4, אבל נזקק לרמז קטן בחישוב או בשאלת ההמשך.
- **2 · בסיסי:** מכיר את המושגים ואת ההחלטות, אבל לא מחשב או לא מסביר את מחיר TCP.
- **1 · לא עומד:** אינו מבחין בין HTTP ל-WebSocket או בין IP ל-DNS.
