קרא קודם את [הפרוטוקול המשותף](../assess-core-knowledge/protocol.md) ופעל לפיו. הקובץ הזה מגדיר רק את התוכן.

**סעיף אפיון:** [6.6 מודל שפה ומודל סיווג](../../../docs/specification.md#66-מודל-שפה-ומודל-סיווג-llm--text-classification).

## מושגי ליבה

### מודל שפה

1. Tokens, ו-next-token prediction לפי הסתברות.
2. Temperature: אקראיות בבחירת ה-token.
3. Context window. אין זיכרון בין קריאות.
4. Prompt ו-schema לפלט.
5. הזיות, ובדיקת הפלט מול schema ומול נתוני OSM.
6. עיקרון בטיחות: ה-LLM מציע, ולא שולט ברמזורים או בשיוך.

### מודל סיווג

7. Dataset מתויג, חלוקה ל-train ו-test.
8. ייצוג טקסט: Bag of Words, ‏TF-IDF.
9. Logistic Regression: משקל לכל מאפיין, הסתברות לכל מחלקה.
10. Accuracy ו-confusion matrix. חוסר איזון בין מחלקות.
11. דליפת נתונים, והטיה כשה-test set נוצר בידי LLM.
12. השוואה בין מסווג ל-LLM: דיוק, זמן ועלות.

## בנק שאלות

### מושג

- **איך מודל שפה מייצר תשובה?**
  תשובה טובה: token אחר token. בכל צעד הוא מחשב התפלגות הסתברות ל-token הבא לפי כל מה שלפניו, ובוחר אחד.
- **מה עושה temperature?**
  תשובה טובה: משנה את חדות ההתפלגות. נמוך: כמעט תמיד ה-token הסביר ביותר, פלט עקבי. גבוה: יותר גיוון ויותר סיכון.
- **למה המודל "לא זוכר" שיחה קודמת?**
  תשובה טובה: כל קריאה עצמאית. המודל רואה רק מה שנשלח בחלון ההקשר באותה קריאה.
- **מה זה TF-IDF?**
  תשובה טובה: משקל למילה לפי כמה היא נפוצה בדיווח, וכמה היא נדירה בכלל הדיווחים. מילים כמו "the" מקבלות משקל נמוך, ו"smoke" משקל גבוה.
- **למה מחלקים ל-train ו-test?**
  תשובה טובה: כדי לבדוק על דיווחים שהמודל לא ראה. בדיקה על נתוני האימון מודדת שינון, לא הכללה.

### החלטה במערכת

- **למה בחילוץ JSON מדיווח קובעים temperature נמוך?**
  תשובה טובה: רוצים פלט עקבי ומדויק באותו מבנה, לא יצירתיות.
- **למה השרת בודק את ה-JSON מול schema לפני שימוש בו?**
  תשובה טובה: ה-LLM יכול להחזיר כל טקסט: שדה חסר, ערך לא חוקי או כתובת מומצאת. המסווג יכול להחזיר רק מחלקה שלמד.
- **למה ה-LLM לא שולט ישירות ברמזורים?**
  תשובה טובה: הוא עלול לטעות או להזות. במערכת חירום החלטה כזו עוברת דרך קוד דטרמיניסטי או מוקדן.
- **למה בניסוי ההשוואה חלק מה-test set חייב להיות דיווחים שאנשים כתבו?**
  תשובה טובה: אם LLM כתב את הדיווחים, הוא נבדק על סגנון שלו עצמו, והתוצאה מוטה לטובתו.

### חישוב או קריאה

- **Confusion matrix.** בנה מטריצה חדשה של 4 על 4 (תאונה, שריפה, רפואי, חסימה) עם מספרים שאתה בוחר. שאל:
  - מה ה-accuracy?
  - איזו מחלקה מתבלבלת הכי הרבה, ועם איזו?
  - למה זה עשוי לקרות? (למשל "תאונה עם עשן" שמסווגת כשריפה)

  תשובה טובה: ‏accuracy = סכום האלכסון חלקי הכול. מזהה את התא הגדול ביותר מחוץ לאלכסון ומציע הסבר מתוכן הדיווחים.
- **חוסר איזון.** אם 85% מהדיווחים הם תאונות, מה ה-accuracy של מודל שתמיד עונה "תאונה"? מה זה אומר על המדד?
  תשובה טובה: ‏85%. ‏Accuracy לבדו מטעה, וצריך לבדוק את המטריצה או מדד לכל מחלקה.
- **עלות.** תן עלות ל-1,000 tokens, אורך ממוצע של דיווח ותשובה, ומספר דיווחים ביום. בקש עלות יומית של ה-LLM, והשוואה למסווג שרץ מקומית.

### מה אם

- מה אם המוקדן כותב דיווח בספרדית, והמסווג אומן רק באנגלית?
  תשובה טובה: המסווג לא מכיר את המילים ונכשל או מנחש. ה-LLM כנראה יתמודד. זו אחת הסיבות לשילוב.
- מה אם ה-LLM מחזיר `"severity": 7` כשהטווח 1 עד 5?
  תשובה טובה: ה-schema דוחה. מבקשים שוב, או מעבירים למוקדן להחלטה.
- מה אם ה-accuracy על ה-test set היא 99%?
  תשובה טובה: חשד לדליפה, או ל-test set קל מדי, או לדיווחים כפולים בין train ל-test. בודקים לפני שחוגגים.

### איתור שגיאה

```python
vectorizer = TfidfVectorizer().fit(all_reports)       # fit on all data
X_train, X_test, y_train, y_test = train_test_split(vectorizer.transform(all_reports), labels)
```

תשובה טובה: ה-vectorizer למד מילים גם מה-test set. זו דליפת נתונים. מחלקים קודם, ומאמנים את ה-vectorizer רק על train.

```python
event = json.loads(llm_response)
dispatch_units(event["required_units"])   # used directly
```

תשובה טובה: אין בדיקת schema ואין אישור. ה-LLM מפעיל שיבוץ ישירות, בניגוד לעיקרון הבטיחות.
